# Shader container decode length — real-function red/green (2026-10-28)

The shared `RenderingShaderContainer::decompress_code` previously treated a nonzero Zstd result as success, including negative error codes and positive short outputs; its raw branch also copied only `min(input, expected)` and returned success. Vulkan, Metal and D3D12 callers treat true as a fully populated stage buffer. This is a correctness defect in the stated function contract, not evidence for a prior unsymbolized access violation.

The candidate keeps the existing single decode: Zstd must return exactly the declared output length; raw input length must equal output length. Failure returns false to the existing callers. It does not add a second decode, hash, or resource scan. The default-off source-key candidate and this fix were combined only in the isolated GREEN diagnostic build; neither engine09 nor the installed engine was overwritten.

Evidence root `D:/code/rmmo_runtime/review_artifacts/shader_decode_red_green_20261028_01/` contains source snapshots, `fixture_identity.json`, build commands/logs/results, all test output and the fixture. RED used the original decoder with the raw module-sharing candidate and the diagnostic bridge. GREEN used the exact-length fix plus the source-key candidate and the same bridge/header bytes. The bridge is exposed only under `RMMO_SHADER_DECODE_TEST_API=1`; it constructs the real Vulkan shader container using its CPU factory and calls the production base decoder directly in a headless process, without a RenderingDevice instance or GPU calls.

Both builds succeeded, restored the shared engine source, and retained the original engine09 EXE/symbol identities. RED EXE SHA `b595e9a33e88bf55d22b3760ea3cdcf89d34cf7369da39a88aac8ab330b7015c`; GREEN EXE SHA `20d25131e638bb6cafa0c285e2cddbf09eb6e7e528ee4f8f22dc566adfd8fde8`. The common bridge/header hashes and RED/GREEN decoder hashes are in `fixture_identity.json`.

The first three RED runs all observed the expected production 6 pass / 8 fail, but their harness exited 1: it incorrectly assumed the untouched tail after a short Zstd decode must retain previous bytes. The actual first positive-short case disproved that assumption. Those three runs remain in `red/run01..03`; their false harness verdict must not be hidden. The common GDScript fixture was then corrected to assert retained tail only on short raw memcpy, not on Zstd. With that one common fixture, the next RED three runs each had **6/8 and expected-red exit 0**; GREEN three each had **14/0 and exit 0**. Every run observed the same scratch allocation for all 14 cases, including the 64-to-48-byte shrink. With the API flag absent, each binary's negative run exited 2 with the expected missing-API message.

Stderr was independently audited: the three corrected RED runs had no error lines. Each GREEN run had exactly five expected Zstd failure/size error lines and three expected raw-size error lines for intentionally invalid inputs, with no other `ERROR` or `SCRIPT ERROR`. Raw stdout/stderr and per-case JSON are retained per run. A standalone registry test was also rerun 100 times in `registry_recheck_01/` with explicit `-UNDEBUG` and a compile-time `NDEBUG` rejection; its compiler command/identity and each result are saved. It tests the exact source-key header, not the integrated Vulkan driver.

These runs prove the decoder's tested success/failure semantics for the fixture; they do not establish the source-key GPU contract or performance. GPU tests and normal map comparisons remain separate.
