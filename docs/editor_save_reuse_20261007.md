# 仅移动物件时复用地图导出资源

用户将“仅移动位置仍反复导出材质与贴图，保存影响工作”列为最高优先级。本次优化同时覆盖 UI 和当前 3D HTTP MCP `save_world`，不修改用户正式地图内容。

**后续反馈（2026-10-07）：用户报告当前城镇地图只修改部分物件的位置，保存仍约十多分钟。保存性能总项已重新打开并保持最高优先级；Grok 初步静态分析后，用户已授权本批修复；新增/删除的增量实现和本轮验证单列于 [增量更新实施记录](editor_incremental_updates_20261007.md)。下文是先前版本、临时副本与特定复用条件下的历史验收，不能作为本次保存已流畅或本次根因已确认的证据。**

本次 Grok 初审及主代理源码复核见 [保存慢静态分析](editor_save_slow_static_20261007.md)。

## 问题与实现

原保存作业每次均重建离屏导出视图并调用 `GLTFDocument.write_to_filesystem`，在新版本目录中重新编码图像。已有 CPU 网格缓存只减少重建工作，不能避免纹理导出。旧测量 `review_artifacts/save_progress/town.json` 中第二次未修改保存仍约 31.89 秒，其中网格准备 0.98 秒、完整导出写入 15.27 秒、验证 13.80 秒；这些是旧版本证据，`write_ms` 也包含几何与 JSON，不等同于纯纹理编码耗时。

新增 `scripts/world3d/pose_save.gd`。同路径可信基线匹配时，只更新 glTF 中承担物件姿态的节点和根作者数据，保留材质、图片、网格、蒙皮、动画及既有依赖引用。普通导入素材移动根 holder；房屋烘焙构件和活动门窗复用 `building_fixtures.transform`，保留枢轴与打开角度。整栋移动同时保存 `building.floor_y`、建筑登记位置、朝向和相应几何签名。未改变的复杂地形/道路留在原资源中；修改地形、道路、河道、岩岸等世界坐标相关构件时仍完整导出。

顶层 glTF `extras.rmmo_save_manifest` 只保存派生导出基线，不进入地图业务 `map_meta`。它核验：

- 源模型和纹理的 SHA256，包括 GLB/glTF 外部依赖及门模型隐式木纹/几何源。
- 引擎、整个 `world3d` 脚本/着色器及导出入口指纹，优先使用进程已加载的实际实现，未加载才读取磁盘代码；开发期间改过脚本后，需要新进程验收。
- 已发布 JSON 原始字节完整性（仅对自己的 checksum 字段置零），以及图片/buffer 的 SHA256 与 buffer 长度。
- 原子保存开始和发布前的地图签名、源资源与已发布依赖；不会覆盖迟到的外部写入。

首次、旧地图缺少基线、尺寸/材质/几何变更、资源内容变化、另存为或验证不成立均回到完整导出。外部源改变时刷新导出资源缓存，避免把新文件签名错误绑定到旧内存像素。另存为创建目标目录独立资源，不引用旧目录。

缺失、越界或损坏的外部模型/纹理直接拒绝保存；完整导出也拒绝 `missing_asset` 占位，不能以紫色方块覆盖原地图。只有已导出的派生依赖损坏、源资源仍完好时，才允许完整重建。

复用仍使用保存锁、`resources_ready`/`before_publish` 注入点、原生 Windows 原子替换、`.previous` 和撤销历史签名更新。失败保持脏状态并解锁界面。UI/MCP 参数不变；结果 `timings.export.mode`、`images_written`、`texture_export_passes` 与 `reused_images`/`reused_buffers` 区分复用和完整导出。

第二轮针对实测校验瓶颈：大文件 SHA 最多使用 4 个独立线程，按文件大小分组；每个文件仍执行资源根校验和完整 SHA，全部线程正常加入后才接受结果。模型文件仍在同一 worker 中先计算 SHA 再解析 GLTF/GLB 外部依赖，不能将后来的父文件签名绑定到先前依赖清单。小于 8 MiB 的集合走串行以减少线程开销。地图只读取一次 UTF-8 bytes，同时完成冲突签名与 JSON 检查；checksum 前置并只修改 64 字节，避免复制整份巨型字符串。发布前仍重新验证源资源、已发布依赖和地图签名，不使用 mtime 替代内容校验。

## 边界

首次建立基线和改变几何/材质后仍完整导出；此版本尚未对一般材质修改实现逐图片增量导出。大地图 JSON 的读取、完整作者数据写入及资源 SHA256 校验仍有成本，不能宣称仅改位置后保存完全即时。已有版本依赖不会主动清理，以保证 `.previous` 可恢复。

## 发布前源依赖复核去重

后续复查确认，复用保存的最终检查还会重新遍历 4372 条记录、解析 GLTF/GLB 依赖 JSON。新增 `verify_source_files` 复用本次保存首次发现的完整依赖集合；每个父模型及依赖仍重新校验资源根、存在性与完整 SHA，全部匹配后再计算生成器指纹。将指纹检查保留在较慢的文件哈希之后，避免接受哈希期间发生的代码变化。首次发现仍完整解析依赖，未信任跨保存的旧清单；父模型新增、移除或重定向依赖必然改变它自己的 SHA，最终检查会拒绝发布。完整导出的 manifest 安装也复用此检查。地图冲突检查、已发布依赖复核、staged 磁盘 SHA 和原子发布保持原样。

Grok 初审 exit 0，subagent 独立复核后实施，根代理复查并调整指纹检查顺序。未采纳将两种不同输入的 SHA 合并、用内存摘要替代磁盘校验、JSON 字节拼接或调整源/已发布依赖并行顺序。材料见 `review_artifacts/save_remaining_20261007/`。

新增 `test_pose_save_source_recheck.gd` 最终 31 项通过：真实新增依赖（文件集合 5→6）、删除、缺失/越界、生成器失配、保持 mtime 和长度但改内容、发布失败保持原图、成功位移及 checksum。原 pose-save 和 SHA 回归通过，真实 HTTP 保存回归也通过。该测试的最小 glTF+manifest 仅是新建临时夹具，未重签旧城镇基线。
