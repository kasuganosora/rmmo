# 流式卸载切帧后的重复候选重建（2026-10-26）

承接 `axel_stream_adoption_20261026.md` 的剩余 20.729ms 候选扫描。本轮只处理
流式操作自身删除节点后丢失计划的问题；不改变加载就绪范围、纹理内容或资源预算。

## 原因与修复

上一轮官方 profiler 的卸载 frame 5798 有 `_apply` 15.019ms，下一帧出现
`_candidates` 20.729ms。`_sync_work` 在单个 `_apply` 超过 10ms 后只保存任务
游标便返回；末尾的 `stream_children` 更新没有执行。下一帧把自身删除导致的
子节点计数下降当作未知 owner 丢失，清空既有目标并重新选择全量候选。

`test_stream_owned_removal.gd` 通过真实 `_sync_work → _apply → _drop` 路径，
给测试 batcher 的 `retire_sources` 注入 11ms 延迟，稳定触发此分支。修复前
首个对象正确移除，但下一帧选择 3,499 个候选、游标退回 0，耗时 22.324ms。
这是生产问题的独立复现，不是只检查新 helper 的实现细节。

修复只让 `_apply` 把当前地图传给 `_drop`。删除的是地图直属节点、而且旧计数
与当前实际计数一致时，在 `free()` 之前扣除这一个已知节点。这样切帧无需靠
末尾兜底，退出回调仍可显式失效，后续未知删除也仍留下计数差。

- 旧计数已经失配或为 `-1` 时不覆盖。
- 嵌套节点、其他 host 上的碰撞体不改地图直属计数。
- 原始 `_drop` 调用默认不认可删除事务，保留已有修复行为。
- `_retire_specs` 的完整索引删除事务不变；没有新增逐节点退出信号或全树扫描。
- `--unaccounted-stream-removals` 仅作为同代码 A/B 对照，正式默认开启修复。

## 保留决定与下一步

保留此修复的依据是：生产分支已独立复现，并在真实地图受控复现中验证；重复
工作明确消失，异常删除修复和回收语义保留，未增加监听/后台任务/资源上传。
不把本组正常整图的时间与 low 变差藏起来，也不把诊断收益替代正常收益。

新的自然 profiler 仍明确显示这些独立瓶颈，后续按同样流程逐项处理：

1. 返回 frame 25598，需求刷新 **36.716ms**，其中 self 25.494ms；
   1213 次距离计算仅 1.244ms。优先找全量扫描、重复建表/排序和可增量维护的
   工作，不能仅减少距离计算或盲目增加 worker。
2. 卸载 frame 7778 为 **61.122ms**；导航移除 15.688ms、worker join 6.002ms、
   索引 `_commit_retire` 10.329ms。`rows` 的 78.238ms 含 worker 聚合，不能
   当作主线程独占时间或与包含范围重复相加。
3. 初始 cover frame 1970 的实际 `Mesh.surface_set_material` **310.420ms**，
   后续仍有 103.284/105.786ms；重载 frame 27085 的实际
   `ArrayMesh.add_surface_from_arrays` 30.546ms。继续用 native 栈定位，
   不重做此前无效的隐藏三角 mesh 预热。
4. cache trim 本次仍有 27.383ms（同帧 8 调用），测试宿主 `track_membership`
   也有 26.165ms。两者要分别归因，不能删掉测试观测后称游戏提速。

当前仍是地图/预制件纹理阶段。未完成完整游戏材质、HUD 等外围阶段，也未达成
整组稳定低于 10 秒或消除全部长帧的结论。
