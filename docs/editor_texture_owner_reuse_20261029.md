# 编辑器整图加载：复用仍由材质持有的纹理

## 结论与范围

编辑器强纹理缓存淘汰后，已发布的场景材质仍持有 GPU 纹理。原 `TerrainTextures.requests` 只检查强缓存，导致同一次加载反复安排同一图片的后台读取和准备；插入的 repair 需求又迫使已有模型预备结果被丢弃重做。

改为查找既有的 `SurfaceMaterials.retained_texture`，复用当前加载已确认且仍存活的对象。实际 axel_town 编辑器 ABBA 中，预制件贴图准备 **629→8 次**，总任务启动 **785–806→60 次**，丢弃重排 **100–121→0 次**，LoadJob 耗时 **261.6–286.7→45.3–55.1 秒**。保留相同的两个 worker、统一字节预算和文档发布顺序；没有启用 lanes/residency 实验、扩大缓存或读取 GLB。

这是编辑器完整文档加载，不是游戏当前需求区域加载，也不是白模数据。OS/驱动缓存未清空，不能声称严格冷启动、p95 或游戏 low 帧已经通过。

## 生命周期和正确性

- `checked` 仍限于一次 LoadJob，首次使用或新一次加载仍通过现有后台准备获取可变文件身份。普通贴图、OpenGL 法线、DirectX 法线保留各自 key。
- 本条记录短期借用已有 Texture2D，覆盖其他贴图准备和发布预算让帧。提交、失效重试或取消时释放，不新增长期强缓存、像素副本或 GPU 上传。
- 发布前重新确认借用对象仍是当前缓存代际。已经启动的导入可能在让帧时刷新来源；此时释放当前像素 lease，回到后台准备，不能把旧对象重新写回缓存。
- 重试不会等待已是 `done` 的旧预排任务；重新规划前清理旧借用集合，启动失败使用最后一次实际请求的完整失败键集。
- owners-only 返回包不触发空图片 install/restore，也不把每条记录都视为异步准备而重置累计分帧计时。GPU owner 留在调用方 wrapper，不混入队列的 CPU-only packet。
- 随后的真实 HTTP gate 又复现了 Cook 本次加载材质池持有旧纹理的问题。现在图片包与已发布 GPU owner 都参与池代际协调；只移除实际过期/失败的材质条目，不修改旧物件、不清无关材质。每次加载记录已协调的 source SHA/representation，普通复用不重复扫描整个池。

这没有为任意外部程序并发改写图片新增全局快照承诺，也没有把纹理存在性等同于来源永久有效。确实失去最后持有者、失败图片或已失效代际仍正常重新准备。

### 同源 PNG 完成结果覆盖已发布 DDS：门控复现与修复

`test_editor_texture_inflight_dds_http.gd` 在真实 LoadJob 的纹理 worker 完成 PNG 解码后、交回包之前用 Semaphore 暂停。主线程随后调用实际导入发布方法，上传同一源 SHA 的 CPU 编码 DXT1，并以测试持有者保留它、把热缓存预算恢复为零；再放行旧 PNG 包。terrain/prefab 都经真实 HTTP open_world 和生产 `_run` 消费，不用隐藏网格预热。

`inflight_dds_red_01` **6 项失败**：两种记录均覆盖 DDS owner、GPU 格式退回未压缩、产生重复上传。旧图片的 SHA 正确，问题是完成结果的表示已被在途导入更新，并非源内容错误。

修复只在既有发布检查中比较已持有的源 SHA 和 representation：当 `source` 图片被同源已发布 `dds:` 取代，先正常归还旧 CPU 包的预算，下一次准备直接借用 DDS owner。没有额外读盘、哈希、GPU 上传或第二个 worker；不改变不同源、未知源或新 DDS 编码的正常发布顺序。

`inflight_dds_green_01` **30/0**、无脚本/引擎错误：两种记录的两个实例都使用相同已发布 DDS，GPU 回读格式 DXT1，每种仅 **1 worker、0 重排、0 追加上传/同步图片读、ledger 0**。另验证未知 SHA、不同源 SHA、新 DDS 表示不会被误判。同目录重跑既有 owner-refresh HTTP **53/0**、无错误。前后源码和候选引擎身份稳定，红样本保留。这里证明并发交付与工作量，32×32 合成色块不作为真实素材 DDS 画质证据，也不从此推导整图加载节省秒数。
