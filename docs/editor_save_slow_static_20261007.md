## 用户反馈与范围

## 复核结论

当前保存是两级处理：**整图通过复用检查，就更新姿态及作者数据；任何一项需要重新生成，就回到整图导出。没有“仅为失效的一小部分重新导出、其他材质/贴图保持原资源”的中间路径。**

最值得优先核对的候选是生成器指纹覆盖过宽，使纯位置修改在进入姿态比较之前便失去复用资格；其次是其他记录/元数据变化或特殊几何类型导致全图回退。即便复用成功，也仍有全记录扫描、多轮内容校验和整份 JSON 重写。**这些机制已从源码确认，但尚未确认本次十多分钟对应哪一条，更不能认定全部时间花在贴图编码。**

它与前一轮“增删调用编辑器 `_rebuild`”不是同一个核心入口：保存作业构建独立导出场景，经过自身复用判定和 glTF 发布；二者共用部分资源和几何代码。保存开始前的结束编辑操作还可能产生额外工作，应单独计时。

## 为什么回退特别昂贵，以及已有优化的边界

- 源或生成器不匹配时，`refresh_sources=true`，会通过 [pose_save.gd:434](D:/code/rmmo/scripts/world3d/pose_save.gd:434) 清相关导出资源缓存；[save_job.gd:119](D:/code/rmmo/scripts/world_editor/save_job.gd:119) 的活动房屋网格复用也被跳过。这是避免新哈希绑定旧像素的保护，不能直接删除。
- 完整路径调用 [gltf_map_io.gd:8](D:/code/rmmo/scripts/world3d/gltf_map_io.gd:8) 的 `GLTFDocument.write_to_filesystem`，再写独立几何 buffer，更新资源 URI 和基线后发布。全导出分支没有项目级跨保存的已编码贴图内容复用。
- 同次保存内已有按材质/纹理对象身份去重、CPU 图像/网格快照、静态几何流式写出及本次 buffer 内的内容去重。保存网格缓存也已存在，不能再概括为“没有缓存”。这些机制不等于跨次保存复用未变图片。
- `save_mesh_cache` 的键包含记录本身，位置改变会使旧键不匹配；但并非所有记录走这个缓存，异步保存还可能先填入活动建筑的新键。Grok 的“位置变就必然缓存 miss”不能当作每件物件、所有实际路径的结论。
- `write_ms` 从 `append_from_scene` **之后**开始，覆盖后续写出、几何完成等工作；`append_ms` 独立记录。Grok 部分文字将它们混在一起，复核已修正。`write_ms` 不能等同贴图编码耗时。
- 保存期间显式关闭编辑输入和预览刷新。因此即使重工作在线程执行，用户仍要等待整个事务结束才能继续编辑；“不再冻结界面绘制”和“保存工作流等待短”是不同目标。

### 源码确认的两道回退

`source_files` 先从当前记录收集并哈希完整源依赖闭包。`_attempt_locked` 390–392 行比较整个 sources 字典；如果依赖路径集合变化，会在姿态/数量检查之前失败，令 `refresh_sources=true`，清相关导出缓存后完整导出。

若资源闭包未变且其他前置条件通过，`update` 333 行仍会因记录数变化返回 `record_count`，转完整导出；这条路径本身不要求清空所有源缓存。**前后两条必须分别处理，不能只放开数量检查，更不能仍按数组下标把旧新记录一一配对。**

| 编辑操作 | 现有回退条件（假定其余基线有效） | 未来应达到的增量行为 |
| --- | --- | --- |
| 只移动/旋转普通模型 | 有机会命中姿态复用 | 更新该实例姿态及必要作者数据，未变资源保持复用 |
| 新增已有素材的另一个实例，闭包不变 | `record_count` → 全导出 | 新增独立 UUID/实例节点，复用相同内容与导出语义下的网格、材质、图片；必要邻接单独更新 |
| 新增模型引入新的源路径或依赖 | sources 不等 → 清缓存、全导出 | 只处理新增和确实失效的资源闭包，不重导出无关旧资源 |
| 删除实例，全部资源仍被其他记录使用 | `record_count` → 全导出 | 移除该实例及必要业务关联，其他实例和共享资源不动 |
| 删除最后引用，令一个或多个源路径退出闭包 | sources 不等 → 清缓存、全导出 | 从当前作者状态移除相应输入依赖；不把“依赖减少”当成其余资源失效，不在这次保存直接删除旧版本仍需的文件 |

这里的“最后引用”按完整路径闭包判断，包含模型外部依赖和隐式门模型/木纹，不等同于素材名称。若该路径仍被其他类型记录使用，就未退出闭包。文件损坏或外部写入冲突等错误仍可提前拒绝保存，不能将“增删必定全导出”表述为无条件忽略错误的结果。

### 动手前需要核实的引用关系

当前 manifest 的 sources 和 dependencies 是两份平面清单，缺少完整的“记录 UUID → 导出节点/几何/材质/图像 → 源依赖与导出版本”归属索引。先核实既有 glTF 能否可靠补建映射，再决定如何增量更新；不能根据同名、同路径或图像像素相同就忽略材质、采样、导出配置等差异。

glTF 实体之间用数组索引引用，节点层级要求严格树结构；skin、动画也引用节点/访问器。因此不能直接压缩旧数组后留下未更新索引，也不能把同一实例节点同时挂在两个父节点下。新增已有素材可共享几何资源，实例节点、动画和骨架关联仍需正确生成。[Khronos glTF 2.0 规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)

Grok 提出保留下标、删除父引用并延后回收，作为降低重编号成本的候选。**主代理不接受它作为无条件安全方案：**骨骼、动画目标、其他有效对象或扩展仍可能引用该节点；保留下标只能避免一类索引错位，不能证明运行时语义正确。必须检查实际活引用、场景成员和扩展要求。未知扩展即使不重编号也不能一概视为安全。新资产局部 glTF 合并同样需要完整、可验证的引用重映射。

源清单应按交集、新增、移除和内容变化分开处理：继续使用的来源必须核验内容，新增来源建立可信导出，退出当前闭包的来源不能牵连未变对象。派生资源的当前 JSON 引用集合与作者源集合不是同一件事；若暂留旧条目或孤儿资源，仍需保持文件与校验一致。

编辑器节点/批次/碰撞更新、磁盘导出增量、废弃资源回收是三个层面。当前地图、`.previous`、保留快照与其他仍使用版本的引用关系未查清前，不回收对应文件。保留资源也不能无限积累，后续需有独立的可验证回收机制；本轮不执行清理。允许必要的地图 JSON 原子发布，不等于允许重新生成整城几何或编码全部贴图。
