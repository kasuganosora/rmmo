# 分块性能验证

运行时分块采用两阶段管线：后台只合成 CPU Image，主线程分帧上传贴图，完成后一次显示整个分块。后台 painter 不进入 SceneTree，碰撞分块字典做快照，PackedArray 保持写时复制，图集只读；关闭或编辑失效时先等待任务退出。

Loading 的 `chunk_handoff` 把现有节点、GPU 贴图、后台任务和未完成上传一起移交给 World。取消加载时由持有对象释放资源；禁止在 apply_bake 中重新同步生成全部分块。加载界面只等待当前视口所需分块，其余方向预加载继续后台执行。

已离开视口的分块采用 96 MiB 上限的保留缓存，重新靠近直接复用节点和贴图。换图、编辑失效会清理缓存。这里的上限只针对离屏保留部分，不包括活跃视口、图集和一个正在生成/上传的分块。

后续增加独立的 32 MiB GPU 纹理备用池：只回收已经隐藏并被完整节点缓存淘汰的纹理，等待三个渲染帧后按尺寸/格式复用；不会改写仍可见的区块。全透明发光通道使用共享零纹理，不为每块上传两张空图。GPU 操作仍在主线程分帧执行，后台只处理 CPU 图像，遵循 [Godot 的线程安全说明](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)。

已保存的中小地图复用 overview.png，避免为每个雷达像素重新合成 48×48 地面。超大稀疏地图仍使用原雷达窗口，不能把它展开为整幅全尺寸图。包内 PNG 通过已有 AssetManager 的有界缓存加载，保留修改时间检查及手动缓存失效能力。

诊断入口：

- `MapField.load_profile`：加载包、预览图、视口就绪耗时。
- `_chunk_stream_module_logic.stream_stats`：生成/恢复/丢弃数，后台、上传、提交最大耗时。
- 临时打开 `MapField.stream_profile_enabled`：记录慢帧的范围刷新、后台任务提交及其余地图逻辑耗时。
- `tools/bench_axel_stream.gd`：真实 Axel256 八个分块的独立基准；命令行 `--` 后可指定结果 JSON 路径。
- `tools/test_chunk_worker.gd`：异步和同步颜色/法线/高度逐像素一致、缓存上限、节点复用、加载阶段移交、任务退出生命周期。
- `tools/test_chunk_prefetch.gd`、`tools/test_chunk_priority.gd`、`tools/test_map_chunks.gd`：方向预加载、传送优先级及旧地图行为回归。
- `tools/test_mv_hotload.gd`：素材发现及包内 PNG 复用已有资源缓存。

性能验收应记录真实行走期间的 P95/P99、最长帧、50/100ms 帧数，并确认确实加载了新分块；站立后观察 60 FPS 不构成流式加载验收。

## Loading 与寻路补充

Loading 复用服务端已解析地图的渲染快照；图像、只读地图数组共享，碰撞对象和流式区块字典独立。编辑器试跑仍重新读取已保存草稿。World 比较规范化绝对路径，避免 `user://` 与绝对路径被误判为不同地图。

首屏队列先完成可见矩形，再补距离和方向预取。`visible_progress()` 返回真正已提交的可见区块数量。`MapField.loading_state` 提供阶段及计数；旧浮点回调仍保持单调。Loading 在可计数阶段显示完成数量，在读取等未知总量阶段只显示状态，保留进度条空间，避免布局跳动。失败信息和返回按钮保留，不倒计时强制离开。

世界资源后台预读。切换遮罩由 GameSession 持有，跨场景存活，到世界首帧绘制后淡出；慢首帧不计入淡出时间。`GameSession.last_loading_progress` 和 `last_loading_profile` 分别保留进度变化及加载、移交、场景就绪、首帧、交互恢复时间。

寻路在每次搜索内缓存单元格通行位，复用四方向、空地和动态占位检查；不跨搜索缓存，因此 NPC 移动或编辑不产生过期碰撞。多目标搜索使用目标包围矩形的八方向距离下界，仍不允许斜向穿角。

## 2026-09-24 实测

Windows，Godot 4.7.2，RX 7900 XTX，Axel256（256×256，48 像素瓦片）。这是开发环境单机测试，不是不同硬件的帧率保证。截图验收与计时分开；加载计时不是清空系统磁盘缓存后的冷启动。

| 项目 | 原实现实测 | 修复后实测 |
| --- | --- | --- |
| 地图预览图准备 | 3970 ms | 3.1 ms，复用已保存预览 |
| 首区块主线程工作 | 1306 ms | CPU 合成在后台；整块节点提交峰值 4.49 ms |
| 后续区块主线程合成 | 98–340 ms/块 | 后台合成，贴图逐帧上传 |
| Loading 渲染阶段再次解析地图 | 约 0.8–1.0 秒 | 快照移交约 1.6 ms（该计时含一次帧等待） |
| 首屏附近场景准备 | 第一轮修复后约 3.2 秒、生成 9 块 | 约 1.59 秒、先生成可见 4 块 |
| Loading 出现到恢复交互 | 未保留可比完整基线 | 2.889 秒，包含碰撞、地图、世界和过渡 |

三轮独立压力测试共 **5219 帧**：18 段传送、0.7/1.3 倍缩放、返回旧区域，最后包含夜间真实寻路行走。记录 0 个超过 100 ms 的帧、1 个超过 50 ms 的帧（53.167 ms）。夜间行走最长 28.488 ms，P99 21.776 ms；当时活跃区块中启用 86 个灯光和 1 个喷泉，水面动画保持开启。节点提交峰值 4.488 ms；单张纹理上传历史峰值仍有 29.12 ms，不能据此宣称已经消除全部尖峰。

报告中的 CPU 数值为 Godot `MEMORY_STATIC`，不是进程 RSS。三轮各阶段约 506–541 MiB；Godot 报告的显存约 568–796 MiB，随区域切换回落。离屏保留缓存始终不超过 96 MiB；这些短时数据不等同于长时间内存泄漏证明。

原始结果保存在工作产物目录 `D:/code/rmmo_runtime/style_work/town_m/`：

- `stream_before.json` / `stream_after.json`：区块阶段基线。
- `stress_autonomous.json`：上述 19 段完整压力测试，包含所有慢帧及阶段计数。
- `stress_pool.json`：纹理复用后的两轮测试，实际复用 126 张 GPU 纹理；`stress_final.json` 是零发光通道压缩后的最终回归。
- `loading_clean_timing.json`：无截图读回的完整 Loading 计时。
- `loading_probe_final/`：进度记录、过渡中间帧和进入后的画面。
- `*.final.log`、`perf_path_tests.log`：回归日志。

复现压力测试：游戏进入 World 后，通过 Godot MCP 的短 `game_eval` 加入 `tools/stress_map_stream.gd` 节点，设置 `output_path` 和 `rounds` 后挂到树根，立即返回。脚本自主运行，每段写入结果；默认 3 轮共约 87 秒。不要把整个测试放进 MCP 的等待协程：该接口 8 秒超时，并且交互调用会影响采样。

新增验证：`tools/test_loading_progress.gd` 检查真实计数、未知阶段、失败入口、可见区块就绪与旧进度回调单调性；`tools/test_grid_path.gd` 对比通行缓存与原始方向/边界/占位规则。`tools/bench_axel_path.gd` 可在 `--` 后传历史寻路脚本路径进行同地图 A/B。

GPU 复用的像素读回另外在实际运行的渲染器中验证：同一纹理对象从红色更新为蓝色，读回为 `(0,0,1,1)`。Headless dummy renderer 不执行真实 GPU 更新，因此 headless 测试只检查对象复用和容量上限，并明确输出跳过 GPU 读回。

最终空发光贴图优化后复测 **1979 帧**：0 个超过 100 ms、1 个超过 50 ms（50.865 ms）；夜间真实行走 P99 **19.367 ms**、最长 **21.729 ms**，地图主线程没有超过 8 ms 的采样，86 个灯光和喷泉继续运行。显存区间降至约 **468–692 MiB**，本轮复用了 67 张纹理。最新加载记录 `loading_final_timing.json` 为首屏准备 **1.596 秒**、Loading 出现到交互恢复 **3.106 秒**。尚有个别约 50 ms 尖峰和单纹理上传约 30 ms 的历史峰值，本次不宣称所有帧严格低于 16.7 ms。
