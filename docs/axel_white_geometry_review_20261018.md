# axel_town 纯网格阶段实测与修复

本轮先从源码和真实运行盲查，不读取旧性能待办。按用户最新顺序，当前只处理无纹理网格的加载、渲染、碰撞和释放；恢复纹理、外围系统和合入另一会话均后置。先前已经完成的修复保留，不据单个总指标决定整条修复链的去留。

## 已确认的纯网格问题

1. 道路的合法 `terrain_follow` 字段未进入依赖目录分类，326 条道路落入全局未知几何。已按现有严格 Road 校验使用冻结几何边界：保守全局记录由 825 降至 499，初始选中记录由 826 降至 515。未取消未知行为的保守回退。
2. 不可变网格先创建 GPU ArrayMesh、再读回并丢弃，绘制面还会重复拆解未涂绘的槽位。已直接保留完整 CPU 通道、材质和精确输出边界，实际发布时再上传；编辑路径保持可编辑来源。
3. 非入口裁剪的加载关闭了碰撞面批量预取，许多很小的网格分别启动工作线程并等待下一帧。已让所有 `LOAD_BUDGET` 加载使用同一有界预取，交互预算仍保持原策略。
4. 批量面提取尚未完成时，普通和分片碰撞路径又为相同 source/CPU/basis 启动重复提取。已等待现有精确任务，线程失败、额度不足和取消仍保留原回退，不等待其他版本的源。
5. 初始导入模型在首次流式接管时集中同步读取 GPU 网格缓冲。直接在后台读取会产生大量渲染器同步往返，已改为在模型提交前分帧准备精确 CPU 网格与碰撞面；私有构建根持有跨帧实例，取消时随根一起回收。背景延迟加载和初始分帧使用相同捕获实现。
6. 显式出生点曾与默认哨兵值混淆，资源驻留会重复线性查找刚发布的记录，静态模板缓存缺少地图生命周期。已分别保留显式参数身份、交接实际记录和按地图弱登记的模板持有关系；私有 GPU 预加载不占用全局模板。
7. 城防碰撞在没有来源变化时仍重复对账，空批次还触发遮挡索引扫描。已按实际来源变更更新，并保留首次建立、删除、碰撞准备与就绪校验。

## 后续方法计时及累计修复

1. 初始私有模型树在入场前生成静态 spec，逆序移除已转移的网格节点，之后才打包剩余原生图。真实模型接管调用从 151.385 ms 降为 0.439 ms；单独这一项没有明显缩短总加载时间，仍保留主线程调用和工作量收益。28 项 GPU 验证覆盖实际变换、材质、碰撞、活动件及动画保留。
2. 冷依赖目录逐个验证 1,058 个唯一规范定义，已改为最多四个后台验证任务；完整规范字节 SHA、长度、字段和所有权校验仍保留，全部任务成功后才分类或发布目录。实际定义验证批次从 5.942 s 降至 2.659 s。整图两组的 cooked 缓存状态不同，不将整图 40.928→35.662 s 全归因于此。目录基础/冷目录/新并行校验分别 42/20/31 项通过。
3. 严格白模没有 terrain ShaderMaterial 时，合批仍构建未被读取的高度/掩码纹理。现在只在实际地形着色器需要时准备；纯标准材质不再依赖掩码元数据。5 项真实 GPU 检查验证几何通道、边界、碰撞与实际合批发布。
4. 加载末尾约 1.7–2.2 s 长帧经 Godot 内置视觉分析器定位在 Forward+ `Setup 3D Scene`：有效记录约 1.648 s CPU，同帧 GPU 约 0.593 ms，不是 GPU 绘制时间。给出无实际地图的 16×16 私有加载视口，复用根视口 AA 设置，在已有加载工作期间完成首帧渲染初始化；仅绘制两帧后停用。无预热组最长帧 1.691 s，两帧预热组约 0.371 s；连续预热与两帧预热分别产生 948/2 次额外绘制。两者总加载时间有波动，不声称两帧方案改善总耗时。10 项 GPU 检查覆盖质量参数、两帧停用、已有相机/后台跳过及退出释放。首帧空场景本身仍约 0.38 s，不能宣称已消除引擎启动成本。
5. 共享帧预算默认关闭时，合批帧回调直接等待尚未完成的线程；加载最后一次同步成员收集也不受分片预算约束。已默认改为帧回调仅回收已完成线程、加载期间分片收集，显式编辑器 `flush()` 仍同步。热缓存同源码对照 `white_batch_warm_blocking/sliced`：最长收集调用 179.577→24.051 ms，运行期活线程等待 16→0 次、213.555→0 ms；累计收集 CPU 139–180 ms 仍存在，分布到多帧。两次最终合批就绪为 22.588/22.233 s，差值较小，收益重点是长调用与等待工作量。原加载预算回归 30 项通过。
6. 方法计时继续锁定 `pavement_abadf19b1171da62ff40` 的网格恢复约 134.799 ms。有材质覆盖的 CPU 来源会提前上传，随后再次进入合批。现将有效覆盖材质保存在每实例 CPU 描述，成员确定后只为未合批来源上传，保留共享源和回退材质身份。`test_sliced_loading_batches.gd` 12 项真实 GPU 检查通过；真实 `white_override_deferred` 不再出现 >50 ms 的 Stream.sync 调用，最终 134 组合批一致。该次加载器 22.020 s / 完整批次就绪 24.536 s，进程间加载器时间波动，不能归为这项修改的总耗时收益。

方法级计时由 `--method-profile` 启用，覆盖 230 余个相关方法；默认关闭，只保留布尔分支。作用域记录包含嵌套调用和 await 挂起，不能相加为 CPU self time；诊断运行本身有额外开销。内置视觉分析器的有效运行是 `white_methods_visual`；尝试原生脚本调用分析器时工具触发了引擎内部 CowData 错误，`white_methods_builtin` 作废，不用作产品故障证据。

## 区块穿越验收范围

用户追加要求后新增 `tools/profile_axel_white_streaming.gd`：在同一严格白模中启用真实 DeferredAssets、AssetResidency 和 NativeResidency；使用生产 `prioritize` / `player_collision` 需求、32 m 区块、交互预算、正常工作线程和 10 秒回收宽限期。导航只运行真实的源目录与回收校验，不烘焙导航网格。控制焦点/相机穿越真实索引物件区，停留卸载后返回重载，再快速折返；此隔离测试不称作角色真实行走或完整游戏性能。

记录每阶段帧分位数、>5 ms 流式调用、发布、区块切换、驻留 spec/网格/碰撞数量、确实删除及重载的 UUID、后台任务与额度。UUID 每 500 ms 观察一次，观察到的移除数量可能低于服务的精确回收计数，不将其当作精确总数。退出另验地图、模板、工作线程、预取面与加载视口归零。最后单独跳转到未完成引用的真实位置，等待任务获得额度后退出，检查飞行中工作回收；这不计作普通行走路径。

首轮 `white_stream_first`：36 次切换，1,327 次实际发布，观察到 402 个 spec 被移除、147 个原 UUID 重载；真实服务记录回收 406 个 spec。无脚本/引擎错误，正常退出归零。但卸载等待最长帧 943.127 ms、返回 774.036 ms、返回后重载 1,064.189 ms，因此没有放行。早期工具只对初始 spec 作白材质替换；后续原始 GLTF 仍保留无纹理材质标量，故此首轮不能当作所有后续来源也已统一白材质的严谨对照。之后已对每次发布的 spec 同样规范化，并保留各槽剔除方向，使用同源码开关重新对照。

定向计时 `white_stream_methods` 确认：`NativeResidency.poll` 最长 953.300 ms，同一次轮询逐个扫描约 14 份完整驻留目录，每次 `can_retire_specs` 约 65 ms，随后全部因 `source_pinned` 拒绝。普通 `AssetResidency.poll` 最长 126.644 ms，成功回收前后重复校验三次。修复将当前渲染/碰撞固定判断提前；真正可回收项仍完整校验，随后在同一个无 await、无回调的事务中与真实导航源目录握手并提交同一个已校验计划。计划不向外部调用者转移，不缓存在地图或历史中。`test_retirement_scan_budget` 9 项验证固定项全图校验 1→0 次、成功项 3→1 次；忙碌导航/非法 UUID 均无副作用失败。

额外回收缺口：私有初始 spec 准备遗漏旧 on-tree adoption 的 `_compiled_resource_owner` 清理。原始 GPU 回归出现三个真实弱引用不释放；空 transform holder 仍持有完整 PackedScene。现只清理已转移全部静态资源的空 holder，保留原生/脚本/灯光等真实图。修复后普通资源 GPU 回归 54 项、原生资源 26 项通过；原生完整楼层、门状态、地形和再加载语义保持。

## 一公里渲染范围之外的回收缺口

`white_native_far_first` 补上从出生点偏移 (2048, 0, 2048) 再返回的真实地图测试，286 次区块切换。远处可见网格/物理实例均为零，但仍保留 5,347 个 CPU spec；原生服务仅回收 70 个单元、216 个 spec。卸载/返回最长帧为 413.849/431.756 ms。最终实际 GPU 白材质审计为 3,832 个槽、零自定义 ShaderMaterial、零非白槽；地图与全部后台额度退出归零。

该轮确认两类问题，而不是资源质量问题：

## 后续所有权缺口的复现与修复

独立回归复现原生回收成功时的三个缺口：共享文档准备表被全量清除，别的已准入任务的道路数组、地形接缝上下文、跨帧材质准备都被提前丢弃。改为仅移除已退役原记录的数组/上下文，同时保留其他仍持有额度的预制件任务所需完整材质条目；无消费者的热材质仍释放。`native_cache_handoff_before` 三项失败，修复后调度 9 项全通过，不再把共享准备表当作全局可清空 LRU。

预制件内容缓存也会因一份定义退役，误删另一份仍使用的相同几何查询项，导致后续重复恢复。现以幸存定义的实际 CPU mesh 身份保留共享项，最后一个别名退出才释放；独立孤儿项继续清理。7 项 CPU 弱引用回归先失败一项，修复后全部通过。普通/原生/导入建筑实际 GPU 生命周期 54/26/24 项复测通过。

索引构建不再给每个部件分配随后被覆盖的临时 bounds 字典，也不再重复扫描整组算原始 bounds；标量桶追加和已验证 ID 表用批量操作，保留原桶和 spec 身份。追加完整/随机等价、退役 70、拥有组退役 48、调度 9 项通过。白模工具另在 CPU 描述上做私有材质投影，首次 GPU 上传也绑定白材质，避免先恢复不用的原受光材质；16 项 GPU 检查覆盖全部原通道、LOD、bounds、准备碰撞、原材质不变、跨实例共享和最终 GPU 释放。

## GLTF 状态数组的重复构造

导入器 CPU 数组候选经过 15 项 GPU 检查，可保持未压缩布局的全部编码通道、LOD、材质和现有缓存失效。实图 `white_importer_cpu_warm` 却证明公会全部 2,007 个网格的 flags=536870912（COMPRESS_ATTRIBUTES），该候选没有覆盖实际格式，仍有 2,007 个渲染服务器数组捕获。候选代码和检查已在外部 `importer_cpu_uncompressed_candidate.gd` / `test_importer_cpu_uncompressed_candidate.gd` 归档，正式路径未替换压缩数据。该实验进入 25.197 秒包含额外扫描，不能当作正式修复性能。

实验进一步暴露了确定的重复工作：`GLTFState.nodes/meshes` 脚本 getter 每次经 `GLTFTemplateConvert::to_array` 构造完整类型数组，相关实现见[当前引擎版本源码](https://raw.githubusercontent.com/godotengine/godot/ed1daf0bf/modules/gltf/gltf_state.cpp)。生成包装器按每个节点重复取这些数组，形成平方级的资源引用复制。现分别在校验、生成后形变恢复阶段各取一次；生成后重新观察，保留扩展新增节点/网格及所有原检查。压缩、顶点与材质数据路径保持。

同源码 `white_state_arrays_repeated/local`，均命中目录缓存、源码/地图前后 SHA 稳定、正确性/退出检查通过：公会 2,318 个节点、2,151 个网格节点，状态数组读取 6,791→4 次，私有生成范围 1,573.701→231.347 ms，白模进入 20.367→17.847 秒。两组主线程源网格数组捕获均为 2,007 次，因此不将该收益归因于减少 GPU 捕获。整段加载还受后台到达和运行波动影响，方法范围和重复工作下降是主要证据。

模型准备 CPU 25 项及实际 GPU 骨骼/动画/独立内嵌纹理回归通过；原始 GLB 15 项再次通过。现有累计修复保留，继续处理大原子发布、完整回收校验及 GLTFState 最后引用释放。

## 大命名空间的私有索引准备
